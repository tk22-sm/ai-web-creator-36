## セキュリティヘッダー・CSP（A2）

実装済み（ローカルで検証済み。D-059・D-060）：
- `npm run build` が `next build` の後に `scripts/generate-security-headers.mjs` を実行し、`out/_headers` を作る（全ページ共通の CSP を `/*` に1つ）。生成・照合に失敗するとビルドが失敗する。
- `npm run check:public` は、`out/_headers` が無い・今のビルド結果と一致しない場合も問題として報告する。
- フォームは JavaScript が動き出すまで送信ボタンを押せない（`disabled`）。`method="post"` と CSP の `form-action 'none'` も併用し、入力内容が URL に付かない。

Cloudflare 上で確認すること（Kai Design 用の Cloudflare Pages プロジェクトの作成について承認を得たあと）：
1. Cloudflare のビルド設定：ビルドコマンドが `npm run build`（`next build` だけにしない）、出力フォルダが `out`。ビルドログに「セキュリティヘッダーを生成しました」と出ていること。
2. ビルド環境の Node.js が 20.11 以上であること（生成スクリプトが `import.meta.dirname` と `fs.readdirSync` の `recursive` を使うため。手元は 22 系で確認）。
3. `curl -sI` で次を確認する：`/`・`/contact`・`/projects/ki-to-hibi`・存在しない URL・`/contact.html`（拡張子なしへのリダイレクト）・`/_next/static/` の .js と .css・`/favicon.ico`・`/_headers`（配信されず 404 になること）。
   - 各応答に `Content-Security-Policy` が **1つだけ**（カンマで連結されていない）付いている
   - 存在しない URL が **404** で返り、CSP が付いている（公式ドキュメントに記載が無いため要確認）
   - `Referrer-Policy: strict-origin-when-cross-origin`・`X-Content-Type-Options: nosniff`（Cloudflare の既定値）が付いている
4. プレビュー URL で、ブラウザの開発者ツールに CSP 違反が出ないこと（全ページ・画面遷移・フォームの入力チェック）。フォームの送信は、実送信の承認が出るまで行わない。
5. Safari・Firefox・実機での表示と CSP 違反の確認。
6. 結果を decision-log に記録する。

## 多要素認証（A3）— 本人が操作
各サービスの設定画面で、次を確認する（認証アプリのコードや予備コードは誰にも共有しない）。

1. **GitHub**：Settings → Password and authentication → 2要素認証が有効か。リカバリーコードを安全な場所に保管。
2. **Cloudflare**：My Profile → Authentication → 2要素認証が有効か。バックアップコードを保管。アカウントのメンバーが自分だけか確認。

5. **Instagram**：2段階認証が有効か。ログイン中の端末に見覚えのないものが無いか。
6. 確認後、このファイルの A3 を「済（日付）」に更新する（具体的な設定内容は書かない）。

## フォームIDの取り違え防止（A6）
1. Formspree では、テスト用と本番用のフォームを名前で明確に区別する（例：「kai-design-test」「kai-design-production」）。
2. 手元の `.env.local` と Cloudflare のプレビュー環境：テスト用フォームID＋`NEXT_PUBLIC_FORMSPREE_ENV=test`。
3. Cloudflare の本番環境：本番用フォームID＋`NEXT_PUBLIC_FORMSPREE_ENV=production`（ID の値はチャットに貼らない）。
4. 設定値は本人が2回確認する（Formspree のフォーム一覧の Integration タブの ID と、Cloudflare の環境変数を見比べる）。
5. 本番の公開後、`/contact` に「テスト用の送信先」「準備中」の表示が無いことを確認する。
6. `production` なのにIDが無い・形式が不正・接続先の指定ミスは、ビルドが失敗する（D-053）。

## 個人情報の保管・削除（A4）— 本人が運用
手順の詳細は `docs/privacy-operations.md`（D-062）にまとめた。要点：

1. **通知・返信メール（専用 Gmail）**：最後のやり取りから3か月以内に、受信トレイ・送信済み・ゴミ箱から削除する。月1回の点検で2か月以上経ったスレッドを削除し、期限までに余裕を持たせる。点検が遅れたときと、対応中の問い合わせの扱いは運用ルールの4章。
2. **Formspree**：対応が終わったら、管理画面で削除できる範囲で速やかに削除する。無料プランの送信履歴は30日分の保存（公式）。受信箱・迷惑メールでの1件ずつの削除と、30日経過後・バックアップ・記録の扱いは公式で未確認のため、プライバシーポリシーでは削除を保証しない。
3. **月1回の点検**：Formspree の受信箱・迷惑メール・Over Limit、Gmail の期限切れのスレッド、2段階認証とログイン履歴。
4. **書き出し（CSV・JSON）・プラグイン・外部連携**：使わない。
5. **AI ツールへの入力禁止**：問い合わせ内容・お名前・メールアドレスを AI ツールなどに貼らない。
6. **契約・請求の情報**：問い合わせとは別の保存ルールで管理する（保存期間は要法務確認）。
7. **Instagram の DM**：フォームが使えない場合の窓口としてプライバシーポリシーで案内する（D-063）。DM の受信テストは未実施（運営者の判断で省略）。Instagram の2段階認証は未確認（A3）。手順は運用ルールの9章。

## 個人情報漏洩が疑われるときの初動対応（A9）
1. **止める**：お問い合わせフォームを一時停止する（Cloudflare の本番環境変数からフォームIDを外して再デプロイすると「準備中」になり、送信されなくなる）。必要なら Formspree のフォームを無効化する。
2. **守る**：関係するアカウント（Formspree・通知先メール・GitHub・Cloudflare）のパスワードを変更し、多要素認証とログイン履歴を確認する。
3. **記録する**：いつ・何が・どの範囲で起きたかを、個人情報そのものを書かずに時系列で記録する。
4. **影響を確認する**：対象となる問い合わせの件数・期間を確認する。
5. **判断する**：個人情報保護法に基づく報告・本人への通知が必要かを確認する（個人情報保護委員会の案内を参照し、必要に応じて専門家に相談する）。
6. **再発防止**：原因を特定し、対策を decision-log に記録してからフォームを再開する。

## 不審な大量送信への対応（A10）
1. **気づく**：Formspree の使用量通知（月間上限の50%・75%・90%・超過）、通知メールの急増。
2. **分類する**：迷惑送信は Formspree の通知メール・管理画面で「スパム」として報告する（判定の学習に使われる）。
3. **対策を強める**（段階的に）：Restrict to Domain の確認 → reCAPTCHA の有効化（JavaScript 送信との両立は事前に確認）→ 有料プランでの高度なフィルター（Formshield の強さの調整・独自ハニーポット）を検討。
4. **本物の問い合わせを守る**：上限超過分は「Over Limit」フォルダに入るため、本物の問い合わせが無いか確認し、必要なら再処理する。
5. **それでも止まらない場合**：フォームを一時停止し（A9 の手順1）、「現在フォームを停止しています」と案内する。
